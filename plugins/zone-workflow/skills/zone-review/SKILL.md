# Zone 審查

讀取目標 repo 的開發準則與 [共用政策](../../references/policy.md)
確認 review 範圍：PR 使用實際 base/head 與 head SHA；本機變更依使用者指定範圍，未指定時涵蓋 committed、staged、unstaged 與新增檔案，分別標示
只使用本次明確關聯票，讀 commit／diff 不擴大票單

## 審查順序

1. **AC**：查詢 Jira 原文，逐條追到實際入口、呼叫鏈與實作位置，列出測試證據及結果
2. **邊界案例**：從本次行為找出空值、錯誤路徑、狀態轉換、重複操作或併發等實際相關情境，避免無依據的假設性缺陷
3. **架構**：對照此 repo 的規則，不引入其他專案架構；引用規則來源與違反位置
4. **品質**：檢查命名、可讀性與重複程式碼，只列會影響本次變更的可行動問題

報告先列有證據的問題：嚴重程度、觸發情境、檔案行號、影響與最小修法
另列尚未驗證的疑點，寫出缺少的證據；沒有可行動問題時明確說明，不湊問題數
附「AC／實作位置／測試」表，測試欄區分既有測試、實際執行結果與未執行
缺 Jira 或 AC 時仍完成可做的程式審查，標示「需求驗收尚未完成」，不能宣稱整體通過

只要求審查時交付報告，不修改程式、不發布 GitHub review 或留言
同一指令明確要求審查並修正時，修正本次問題、保留既有工作區變更並執行適用驗證；無須重複索取修改授權

完成條件：指定範圍已覆蓋，每條 AC 有判定與證據或明確缺口，問題與疑點分開，驗證限制已回報
審查本身不授權 push、PR 發布或合併；需要發布時再依 [PR 流程](../zone-pr/SKILL.md) 執行
