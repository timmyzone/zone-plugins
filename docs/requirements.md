# PR 與審查需求

狀態：已於 2026-10-20 授權實作；實作與驗證狀態見 validation.md
更新：2026-10-20
分發方式補充：2026-10-21

## 已確認範圍

- 供 Zone 各專案的 teammate 使用，支援 Claude 與 Codex 安裝及更新
- 團隊各自付費，透過具有讀取權限的 GitHub repo 自行安裝／更新；不提交公有 plugin 目錄、不依賴企業 workspace 管理後台
- 共用能力涵蓋 PR 與審查，exchange-server、lending bot 等專案的架構留在各 repo
- PR 範圍包含功能 PR，以及將 release 分支合併回 main 的 PR
- 交付的 plugin 自帶所需 skills、流程與模板，執行時不依賴另外安裝的 skills
- 可參考 wf-pr 的能力與模板；其個人預設不直接視為團隊政策
- 審查以「確認需求做對，而不只是程式沒有錯」為核心

## 審查順序

1. 逐條對照 Jira AC，判斷是否滿足
2. 檢查邊界案例
3. 對照適用專案的架構規則
4. 檢查命名、可讀性與重複程式碼

審查標準可取自指定 Notion 與各專案開發準則

### 審查操作範圍（已確認）

- 審查先提供 AC 缺口、問題位置、影響與建議修法，不自動修改程式
- 使用者要求修正時才進入修改與驗證；若同一指令已明確要求審查並修正，不重複索取授權
- 審查報告須區分有證據的問題與尚未驗證的疑點

| --- | --- | --- |

### Jira 與 AC 缺漏（已確認）

- 沒有 Jira 票或解析後的驗收來源主票沒有 AC 時，可繼續程式審查與產出草稿，但停止 PR 發布，補齊後重新檢查
- 2026-10-21 補充：主票使用自身 AC／修正版本；子任務沒有這些資料，須依 Jira parent 找主票取得，不因子票欄位為空而停止
- 保留子票 → 主票對照；子票範圍對照主票相關 AC，範圍不明先釐清，不擴大到兄弟子票或宣稱整張主票完成
- 2026-10-21 例外：來源分支為 chore／refactor（含各自的 `/名稱` 分支）且無關聯票時，不硬性要求 ticket，免 Jira AC／版本比對；仍驗證目標分支、審查與測試。有關聯票時仍完整檢查
- 資料缺漏時，報告須標示需求驗收尚未完成，不能以程式審查無問題代替 AC 通過

### 本次 PR 關聯票範圍（已確認）

- 只檢查本次 PR 明確關聯的 Jira 票，功能 PR 與 release → main 均適用
- 票單取自使用者對本次 PR 明確指定的關聯票，以及本次 PR 明確列出的 Jira 關聯資訊；去重後逐張檢查
- 分支歷史與歷史 commit 中出現的票號不自動加入票單，讀取 diff 或 commit 也不擴大檢查範圍
- 本次明確關聯多張票時，每張均須符合適用 AC 與目標版本門檻；子票取其主票資料，共用主票不擴大本次票單
- 無法確定本次關聯票時，列出缺口並停止發布，不從歷史票推測補齊

## 版本門檻：使用者提供的允許案例

| Jira 修正版本 | PR 目標 | 條件 |
| --- | --- | --- |
| `6.2.0*` 或 `v6.2.0*` | `release/v6.2.0` | `*` 為零個或多個任意字元，包含數字 |
| `6.4.0*` 或 `v6.4.0*` | `main` | 遠端最大 release 版本為 6.3.0，下一個 minor 為 6.4.0 |

### 共用修正版本比對（已確認）

- 每張驗收來源主票只有一個修正版本；子任務使用主票版本
- 不實作多版本選擇邏輯；讀到零個或多個版本時停止發布並回報資料不符預期
- Jira 版本名稱去除前後空白與開頭可選的 `v` 後，以預期版本 `X.Y.Z` 做字串前綴比對
- Jira 修正版本以 PR 目標版本為準，不以來源分支版本替代
- 目標為 release 的預期版本取自目標分支；目標為 main 的預期版本依下節推導，兩者使用相同比對規則
- `*` 可為空或任意字元序列，包含數字；不是只允許括號或非數字後綴
- 目標為 `release/v6.2.0` 時，接受 `6.2.0`、`v6.2.0`、`6.2.0(後端)`、`6.2.0-hotfix`、`6.2.00`、`6.2.01`
- 同一目標不接受 `6.2.1`、`6.3.0`、`16.2.0`
- 使用者已明確確認數字後綴也接受；取代先前擋下數字後綴的建議
- 此比對不能當作語意版本相等判斷，例如 `6.2.01` 也符合 `6.2.0*`

### main 目標版本推導（已確認）

- 從遠端 release 分支取得最大版本，按 major、minor、patch 數值比較
- 最大版本為 `M.m.p` 時，main 的預期版本為 `M.(m+1).0`，套用上節共用修正版本比對
- 這是團隊採用的版本政策，不代表能從分支推知任意發布計畫
- 不新增或要求各 repo 維護 main 版本文件
- 最大 release 為 6.3.0 時，`6.4.0`、`v6.4.0(後端)`、`6.4.01` → main 通過；`6.5.0`、`7.0.0` → main 擋下
- 無 release 分支或遠端查詢失敗時停止；跳版與 major 升版先擋下

### release 合併回 main（範圍已確認）

- 此流程將 release 分支累積的修改合併回 main
- 版本檢查仍以目標 main 的預期版本為準；撤回以來源 release 版本檢查的提案
- 依目前規則推得：最大 release 為 6.3.0 時，main 預期 6.4.0；接受檢查的 Jira 票若仍為 6.3.0，會被擋下，不自行修改 Jira
- 已確認的 Merge commit 與 auto-merge 策略仍適用

## PR 自動合併（已確認）

- 使用者要求建立／更新 PR 時，完成版本與發布門檻檢查並發布後，自動啟用 auto-merge，不另詢問是否啟用
- 只要求草稿內容、預覽或審查時，不構成發布或合併授權
- 透過 GitHub 的正常合併機制等待必要檢查與審查，不繞過合併保護
- 若 repo 未設定必要檢查或審查限制，啟用 auto-merge 可能立即合併；使用者已選擇此流程
- 回報時區分「已啟用 auto-merge」與「已完成合併」，各自取得對應的 GitHub 狀態證據；失敗則如實回報
- 此決策定義交付 skill 的行為，不授權本次對話操作其他 repo 的 PR 或保護設定

### 合併方式（已確認）

| Head | Base | 方式 |
| --- | --- | --- |
| `merge/*` 或 `release/*` | `release/*` 或 `main` | Merge commit |
| 其餘組合 | 已通過版本門檻的目標分支 | Squash |

沿用 wf-pr 的合併方式選擇；此表不擴大允許的目標分支或版本範圍

## 第一版實作範圍（已授權）

- 在此 repo 封裝一個 plugin，提供 PR 與審查兩個 skills，共用同一份版本規則與模板，不呼叫外部安裝的 skills
- 目標介面為 Claude Code 與 Codex；各平台使用原生 manifest／marketplace，維護同一份 skill 內容
- 安裝、更新與回退文件以實作時核對的官方支援方式撰寫，實際未驗證的介面與版本明確標示，不宣稱全平台實測通過
- release 名稱：辨識 `release/vX.Y.Z` 與 `release/X.Y.Z`，實際 PR base 必須明確且存在遠端；若版本別名對應兩條分支，停止並要求指定完整分支
- Jira 或必要規範查詢失敗時保留可完成的審查與草稿，停止發布，不將無法查證當作通過
- 專案架構由各 repo 的開發準則提供，plugin 不內建 exchange-server 或 lending bot 的架構
- 驗證涵蓋封裝格式、內部引用、自包含性，以及版本、關聯票範圍與發布門檻的正反案例
- 交付 plugin、安裝更新說明與驗證結果；已連結 timmyzone/zone-plugins，使用者於 2026-10-21 明確授權 commit／push
